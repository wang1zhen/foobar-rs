# DSP / 可视化 WASM 音频沙箱：可行性评估（M5）

结论先行：**M5 只做可行性评估，不把 WASM 接入实时音频链。** 当前 WASM 宿主只覆盖声明式命令/面板；DSP/可视化需要单独的 ABI、独立线程和可量化的延迟验收，不能沿用 M5 的同步命令调用路径。

## 为什么不能直接放进实时音频回调

实时回调通常只有几毫秒预算，要求无锁、无阻塞、无不可控分配。把 wasmtime 调用放进回调有几类风险：

- **执行时间不可预测**：插件循环、内存增长、trap、fuel 计数都会引入抖动；fuel 只能限制总量，不能保证单个 block 在 deadline 前返回。
- **分配与锁**：跨宿主/guest 边界、Store 访问和宿主函数可能分配或加锁；实时线程不能等待音频线程之外的资源。
- **JIT 与平台差异**：模块在加载时编译，但 Cranelift JIT 的可执行内存、平台安全策略和 CPU 差异仍需三平台验证；解释器 fallback 的实时性也未测。
- **故障传播**：trap、panic 语义、内存上限触发都可能发生在回调内部；错误必须在音频线程之外处理。
- **可视化同步**：UI 帧率与音频 block 不同步，直接回调推送会阻塞或丢帧。

当前宿主没有 epoch/墙钟超时，只有 fuel 和内存/表/实例上限，因此更不能把不受控插件放进音频回调。

## 建议架构

如果后续要支持 DSP：

1. **离线或分段处理**：先支持整首/整段离线处理（导出新文件、分析、响度等），不进入播放链路。
2. **独立 DSP 线程 + 有界队列**：音频线程只做实时供给；DSP 线程按 block 取数据、处理后写回环形/有界缓冲。队列满或插件超时直接 bypass，不阻塞音频线程。
3. **预分配缓冲**：所有输入/输出缓冲和插件实例在播放前创建；process 调用内禁止分配、文件/网络访问和宿主回调（除必要的参数快照）。
4. **明确 block 大小与延迟预算**：固定或限定 block（例如 64–512 帧），以实际 buffer deadline 为准；开始前声明引入的延迟，seek/切换时清空状态。
5. **可视化走快照**：DSP/分析线程把频谱/电平快照写入有界共享结构，UI 按帧读取；禁止在音频回调里调用插件或等待 UI。

## 需要的最小 ABI（若继续）

当前 M5 命令 ABI 只传标量，不满足音频数据交换。最小设计应包含：

- 宿主在 guest 线性内存中提供固定布局的 planar `f32` 输入/输出缓冲；插件导出 memory 或由宿主通过 ABI 取得指针。
- 一次处理一个 block 的入口，例如 `fb_dsp_process(frames: i32, channels: i32, in_ptr: i32, out_ptr: i32) -> i32`，返回状态码；禁止在 process 内分配。
- 初始化/配置入口：采样率、通道数、最大 block 帧数、参数；返回所需延迟（samples）和是否支持 in-place。
- 版本化参数快照；参数变更不能在 process 中阻塞。
- 失败语义：非零返回/trap 即 bypass 当前插件并记录错误，音频继续输出干声。
- 不链接 WASI；DSP 插件不得访问文件/网络/凭据。

## 验收指标

接入实时链前至少需要（当前均**未测量**）：

- 最坏情况和 p99 的单 block 处理时间，相对音频 deadline 的余量。
- 长时间运行（至少 10 分钟）无 dropout、无内存增长、无分配尖峰。
- 三平台（Linux/Windows/macOS）JIT 与线程调度差异。
- 插槽绕过/启用、采样率切换、seek、设备切换时的状态清理。
- 故障注入：trap、无限循环、内存超限、缺导出时音频不中断。

## 结论

M5 只交付本评估和命令/面板 SDK；DSP/可视化保持“未实现”。真正接入前需要单独的里程碑，先做离线/分段处理，再评估独立 DSP 线程和上述 ABI；在拿到 p99/最坏 block 时间和三平台数据前，不承诺实时音频支持。
